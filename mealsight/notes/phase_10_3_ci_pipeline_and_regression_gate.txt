EVALUATION SUITE LEGITIMATELY FAILS

no regressions, not a perfect score."

---------------------------------------------------------------------
2. DESIGN DECISIONS AND WHY
---------------------------------------------------------------------

2.1 REGRESSION, NOT ABSOLUTE PASS.
Dimension 1 (photo ingredient recognition) scores 0.488 against a 0.60
threshold for a documented external reason: the original vision model
was retired and the replacement tier is the only one reachable on the
free plan. Gating on the overall verdict gives a permanently red
pipeline, and a permanently red pipeline trains everyone to ignore it.
Rejected alternatives: lowering the threshold (dishonest: moving the
goalpost to make a number pass), marking the job continue-on-error
(green regardless: a gate that cannot fail), skipping Dimension 1
(hides the one place the model can drift).
What I did: baseline JSON in the repo; the dimension is flagged
known_failing with its reason; the gate fails only if it falls below the
known level minus tolerance. If it ever recovers, the gate says
RECOVERED and asks for a baseline refresh, so improvement is recorded
rather than silently banked.

2.2 TOLERANCE BASED ON EVIDENCE.
Dimension 1 moved between 0.485 and 0.492 over five runs, so its band is
just wider than that spread. Case-count dimensions get one case of
tolerance. Dimension 3 (deterministic arithmetic) gets zero. A band
wider than the evidence hides real regressions; narrower produces false
alarms. Each tolerance is recorded with its noise evidence in the
baseline.

2.3 INVARIANTS ARE NOT SCORES.
Some properties must hold exactly: zero hard-constraint (allergy/diet)
violations, zero matcher disagreements, zero case defects, real
databases untouched. These are checked as equality, not as a number
within a band. A safety property averaged into a score can be hidden by
other cases passing.

2.4 THE GATE PROTECTS ITSELF.
It fails on: a dimension missing from the scorecard, a changed pass
threshold (nobody lowers the bar quietly), fewer cases than baseline
(cases silently dropped), unreadable scorecard or baseline (exit 2, so a
broken gate never reads as green). Refreshing the baseline preserves
tolerances, statuses and invariants, so a refresh cannot quietly widen a
tolerance or relabel a failing dimension. Baseline changes are meant to
be reviewed in the same diff as whatever moved the numbers.

2.5 DETERMINISTIC DATA FOR A DETERMINISTIC TEST.
Dimension 3's expected answers were derived by hand against a specific
recipe corpus. The corpus came from a live API (not reproducible) into a
gitignored database (absent in CI). Solution: export 250 recipes to a
committed JSON snapshot with a count and sha256 in its metadata;
load_snapshot verifies both before inserting; the seeder gained a
--from-snapshot flag. The gate's --strict-data flag then fails if the
rebuilt reference data hashes differ from those the baseline was
recorded on, so "the test data drifted" is caught as a distinct, named
failure instead of looking like a matcher regression. The snapshot
reproduced all four recorded data hashes exactly.

2.6 SECRETS AND COST.
PR workflow uses no secrets at all (also true of fork PRs, which GitHub
withholds secrets from anyway). The nightly exposes the three keys to
exactly one step, via step-level env, never echoed. Nightly cost is
~426k tokens (~12.8M/month). Against the known ministral-8b limit
(625k tokens/min, 3.13 req/s) a run uses ~4-6% of the per-minute
budget, because the run spreads over 11-17 minutes. The monthly free-tier
allowance is not documented in the repo, so real headroom is UNKNOWN; I
said so, and documented the dial (weekly cron, or Dimension 2 --sampled).

2.7 SHA-PINNED ACTIONS.
Tags are mutable; a compromised or force-moved tag runs attacker code
with your secrets. Pinning to the commit SHA with the version in a
comment, plus Dependabot to keep them current, gives reproducibility
without staleness.

---------------------------------------------------------------------
4. WHAT THE CI EXERCISE FOUND
---------------------------------------------------------------------

4.1 REAL PRODUCT BUG: MCP SUBPROCESS ENVIRONMENT.
The client launched each MCP server subprocess with only a handful of
"safe" variables. A server could therefore read an API key from a .env
file but not from a real environment variable, which is how every CI
system, Docker container and cloud host supplies secrets. In production
under those conditions every server would have failed to start. It never
showed locally because a .env file always existed. Fix: the child
environment is the parent's environment plus any explicit extras
(_subprocess_env). Regression test added. Interview value: "CI found a
deployment bug that local development could not, by simply being a
different environment."

4.2 TEST HERMETICITY.
Tests asserting "no key configured" behaviour passed only if the
developer's .env was absent or present in a specific way. Fixed with
autouse fixtures that delete the three key variables (settings tests)
and set a fake key (weather tests). Principle: a test must define its
own world.

4.3 THE FLAKY WEBSOCKET TEST (test_ws_mid_run_receives_buffered_then_live_messages).
The brief said it was timing-sensitive and asked whether it flakes in CI
and to handle it deliberately.
Honest finding: I could NOT make it fail. Before any change: 0 of 30
idle runs and 0 of 40 runs on an 8-core machine under 16 busy-loop
processes. After: same, 0 failures. So I cannot claim to know whether it
flakes on GitHub's runners.
What I did anyway: the test used sleeps to guess when the server had
buffered messages. I rewrote it with threading.Event: the server side
signals "emitted", the test waits on that event (bounded), asserts the
live message has NOT been released yet, then releases it and asserts
delivery order. Now it asserts the actual property (buffered first, then
live) with no timing assumption.
Why not retries: a retry on a flaky test hides real races. No automatic
retries exist anywhere in the pipeline; if something flakes it should be
visible.

4.4 EVAL PROCESS HANG: see story step 5.

5. MY OWN MISTAKES (TELL THESE HONESTLY)
---------------------------------------------------------------------

- Load-test cleanup. To test the flaky test under CPU contention I
  started busy-loop background processes. The test commands timed out
  before my cleanup ran, leaving 32 spinner processes and a load average
  above 300. My first kill did nothing because zsh does not word-split
  an unquoted variable, so the kill got one long string and failed
  silently; I then trusted a count that said "1 remaining" without
  rechecking. A broad pkill was (correctly) blocked by the safety layer,
  and I switched to killing exact PIDs after confirming each was my
  spinner and not the user's own busy process. Lessons: cleanup must be
  guaranteed (trap), verify the outcome after acting, and never use
  broad kill patterns on a machine with someone else's work on it.
- Shell portability slips: GNU sed -i vs macOS (needs an empty suffix);
  no `timeout` binary on macOS.
- YAML: an unquoted colon inside a step name is a mapping, not text.
  Caught by parsing the file before committing.
- Scope slip: I first ran mypy over everything; the tests carry ~17
  pre-existing strict errors. I scoped CI to mealsight and eval and
  documented the debt rather than pretending it was clean or silently
  expanding the task.
- Verification honesty: no real GitHub Actions run was possible from my
  environment (CLI not authenticated, nothing pushed at that time), so
  the "successful run with timing" was from the clean replica and I said
  so in the report, rather than implying a hosted run.


---------------------------------------------------------------------
6. PRINCIPLES
---------------------------------------------------------------------

1. A gate should enforce a promise you can keep. "No regressions" is
   keepable; "everything passes" was not.
2. A permanently red pipeline is as useless as a permanently green one.
3. Safety properties are equalities, quality metrics are bands.
4. Tolerances need evidence, and the evidence lives next to them.
5. The gate must be able to fail, and must fail when it breaks.
6. Reproduce on a clean machine before trusting any pipeline.
7. If you cannot reproduce a flake, say so, remove the fragility you can
   identify, and do not paper over it with retries.
8. Least privilege: read-only token, secrets on one step, pinned actions.
9. Do not lower thresholds to make numbers pass; change the bar only in
   a reviewed diff with a stated reason.
10. Report what was not verified.

8. LIKELY INTERVIEW QUESTIONS
---------------------------------------------------------------------

Q: Your eval suite fails. How can CI pass?
A: CI gates on regression versus a committed baseline, not on the
   absolute verdict. The failing dimension is recorded with its reason
   and tolerance; it fails the gate only if it gets worse. Safety
   invariants have zero tolerance.

Q: Isn't that just lowering the bar?
A: No. The threshold stays 0.60 and the dimension is still reported as
   failing. What changed is what the pipeline enforces. And the gate
   fails if anyone changes the threshold, drops cases, or loses a
   dimension, so the bar cannot move quietly.

Q: How do you handle nondeterministic LLM output in a gate?
A: Split by determinism. The matcher dimension is pure arithmetic: exact
   equality, runs on every PR, free. The LLM dimensions get measured
   tolerance bands and run nightly. Invariants never use bands.

Q: How did you make the DB reproducible?
A: Pinned snapshot of the corpus with a checksum, verified on load, plus
   a --strict-data check in the gate so data drift is a named failure.

Q: How did you deal with the flaky test?
A: I tried to reproduce it, couldn't (70 runs including CPU starvation),
   said so, removed the sleep-based timing with event synchronisation,
   and declined retries because they mask races.

Q: What would you do about the monthly API quota?
A: It's unknown from the repo, so I flagged it instead of guessing:
   nightly is ~12.8M tokens a month. Dials: weekly schedule or sampled
   Dimension 2. I'd also check the provider's usage page after the first
   week.

Q: What did CI teach you about the product?
A: The MCP servers didn't inherit environment variables, which would
   have broken every real deployment. Local .env files hid it.

Q: Security of the workflow?
A: Read-only token permissions, no secrets in PR runs, secrets scoped to
   one step, SHA-pinned actions with Dependabot, concurrency control.

Q: What would you improve next?
A: Make tests mypy-clean and add them to the check; run the nightly on
   a rolling window and alert on trend, not only threshold; cache the
   eval's model calls for cheaper reruns; add a path filter so docs-only
   PRs skip the heavy jobs.

A1. THE CLEAN-RUNNER PANTRY BUG (second "works on my machine" defect)
---------------------------------------------------------------------

WHAT HAPPENED. The first hosted run of the matcher-gate job failed with
sqlite3.OperationalError: no such table: pantry.

ROOT CAUSE. eval/runner.py calls pantry_snapshot() at the start of every
run, to record a provenance hash of the pantry. That queries the pantry
table. CI seeded recipes.db from the snapshot but never created or
seeded pantry.db. Locally it worked only because the database files had
existed for months. Same shape as the MCP environment bug in section 4.1:
a hidden dependency on state that only my machine had.

THE DESIGN DECISION (a good interview story): fix it in BOTH places.
  - Make the runner tolerant. Dimension 3 carries its own pantry state in
    its cases and needs no pantry, so requiring a seeded pantry just to
    record a hash coupled a dimension to data it never uses. If the
    pantry is absent the runner now RECORDS it honestly:
    pantry_present: false, rows_at_run_start: null, content hash: null,
    plus the error text. It never writes the hash of nothing.
  - But also seed the pantry in CI, because Dimensions 1, 2, 4, 5 do need
    the demo pantry, and a provenance record with no pantry is weaker.
  - And make the gate enforce it: the baseline now stores the pantry
    content hash (c975c014058a) and row count (64). With --strict-data an
    absent or different pantry FAILS any run containing a pantry-dependent
    dimension; for a Dimension-3-only run it is only a note. So tolerance
    in the runner never turns into silent acceptance in the gate.

WHAT ELSE WAS MISSING (found by running on a truly clean directory):
  - scripts/reset_demo_pantry.py assumed the schemas existed. It now
    creates the data folder and applies all three schemas (idempotent).
  - The shelf_life_reference table lives in the PANTRY database and
    nothing seeded it on a fresh checkout. Without it the shelf-day
    numbers, and therefore the pantry hash, would have differed even with
    the table created. The script now loads it from committed JSON.
  - The script hung at exit because schema init opened the user database
    and nothing closed it (same family as the eval-runner hang in section
    3 step 5). It now calls close_all().

HOW I PROVED IT. Fresh directory containing exactly what a commit would
contain: zero database files, zero .env, no venv. Ran every ci.yml step
in order with env-var placeholders only. Result: pantry hash
c975c014058a, 64 rows, matching the baseline. Also re-created the
original failure (pantry.db absent): the run completes, records the
absence, and the Dimension 3 gate still passes.

AUDIT FOR OTHER FRESH-CHECKOUT ASSUMPTIONS. Searched for anything that
assumes a database file, cache dir or .env already exists. Everything
else was already safe: .env optional (env vars win), data dir created on
demand, vision checkpoint file skipped if absent, TheMealDB cache dir
created when needed, test images tracked in git.

LESSON. Two defects of the same shape (env inheritance, unseeded DB) means
the shape is the lesson: a pipeline's first job is to be a machine that
has none of your accumulated local state. I should have asked "what does
a runner have that my laptop has?" before the first push, not after.

TESTS ADDED: absent/different pantry fails strictly for pantry-dependent
dimensions; Dimension-3-only gate does not need a pantry; runner records a
missing pantry and never hashes nothing.

A2. PREFLIGHT, CIRCUIT BREAKER, SECRET HYGIENE, STEP TIMEOUT
---------------------------------------------------------------------

WHAT HAPPENED. The first hosted nightly burned 45 minutes and was
cancelled. Every Dimension 1 call returned 429 on its first attempt, was
retried four times with 2/5/10 s backoff, then failed. The same key
returned 200 locally. My first suspect: a trailing newline pasted into
the GitHub secret.

FOUR LAYERS OF DEFENCE (each added for a distinct failure mode):

1. Whitespace stripped at load (settings). A pasted newline is invisible
   and breaks authentication. Secrets are now stripped when loaded. A
   whitespace-only required key still fails as "blank".

2. Preflight step (python -m eval.preflight). Before any dimension runs it
   makes ONE trivial call per provider and prints the status plus every
   rate-limit header, and reports each key's LENGTH and whether it has
   leading/trailing whitespace. It never prints a key. It fails the job in
   seconds on 429, 401/403, 5xx, unreachable, or too-low throughput. Padding
   alone warns (the strip already neutralises it) but does not fail.
   Verified with a real key plus a deliberate "\n": reported as length 33,
   TRAILING whitespace, control character; settings loaded it as 32.

3. Circuit breaker (eval/circuit.py). KEY INSIGHT: the provider layer
   retries and the perception/reasoning layers above deliberately swallow
   failures into fallbacks, so a run where every call 429s used to
   produce a scorecard with Dimension 1 near zero. That is an
   INFRASTRUCTURE failure recorded as a QUALITY score, and if the gate
   ever accepted it as a baseline it would poison every later comparison.
   Fix: the provider layer now publishes the FINAL outcome of each call
   (ok / rate_limited / provider_error / auth_error) to an observer
   (providers/outcomes.py); the eval harness subscribes. Within one
   dimension, once at least 5 calls have finished, if 50% or more failed
   after retries, the run ABORTS.
     Threshold reasoning: each counted failure already survived 4
     attempts, so it is outage-grade, not a blip; 5 is the smallest sample
     where "half failed" is not one unlucky call and it bounds the cost of
     an outage to ~5 calls of retry time (about 90 s) instead of the whole
     run; 50% leaves room for a few real transient failures in a long
     dimension.
   On abort: scorecard records aborted:true + the reason and counts, the
   suite exits 3 (0 pass, 1 suite FAIL, 3 aborted), the workflow fails
   immediately with an error, and eval.compare REFUSES the scorecard
   (exit 2) including for --update. An outage can never become a score or
   a baseline.
   Tested with real retry code and mocked responses: a 100-call loop of
   429s stops after exactly 5 calls (20 mocked attempts, zero real I/O).

4. Timeouts. Suite step 30 min (~2x the slowest observed real run of 17),
   preflight step 3 min, job 40 min (was 45 with no step limit).

THE PLOT TWIST. The preflight's first real run showed the headers
x-ratelimit-limit-req-minute: 2. The 429s were probably NOT the newline:
the key was genuinely limited to 2 requests a minute. The preflight was
extended to fail when a provider allows fewer than 10 requests/minute
(a full run needs ~9/min), with a --min-rpm flag. That is A3.

LESSON. I built the defence against the hypothesis I was handed (bad
secret) and the tool I built immediately showed the real cause was
different. Building diagnostics that report facts, not just verdicts, is
what let the evidence overrule the hypothesis.

MISTAKE TO ADMIT. I truncated eval/preflight.py by opening it for
writing before reading it in the same statement; I noticed because a grep
returned nothing, and rewrote it in full. Shows why verifying edits
matters even for "trivial" one-liners.

WHAT I DID.
  - Updated MODEL_RATE_LIMITS to rps=2/60, tpm=40_000 with a dated
    comment: measured from headers, restructured mid-project, RE-VERIFY
    DO NOT TRUST. Removed stale "3.13 RPS" mentions in comments and the
    settings test (which now asserts the measured values).
  - Nightly eval: removed the cron schedule, kept the workflow and manual
    dispatch, with a header comment: the provider reduced throughput
    mid-project, not a defect in the suite; how to re-enable. Manual runs
    take a min_rpm input; at 2 requests/min the preflight fails in
    seconds, on purpose.
  - Dimension 3 still runs on every PR: no API calls, <1 s, a genuine

THE COST PICTURE (a nuance interviewers like). A full run is ~426,000
tokens, about 4 cents against the $10 monthly included allowance (figure
from the account; pay-as-you-go disabled so no charge is possible).
TOKENS ARE NOT THE CONSTRAINT; THROUGHPUT IS. 118 calls at one per 30 s is
about an hour of rate-limit waiting, longer than the job timeout. This
reverses my earlier section-2.6 analysis, which assumed the old limits.
Be ready to say so plainly: the earlier analysis was correct for the
numbers I had and wrong for the numbers that existed.

WHAT THE OLD LIMITER WAS DOING. It was pacing ~100x too fast, so it let
calls through that the provider then 429'd, and the retry/backoff layer
turned each into long stalls. This explains the "single-call hangs" seen
during development. Measured: a text-only recommendation that worked at

A4. HEARTBEAT COVERAGE FOR EVERY WAITING STAGE
---------------------------------------------------------------------

THE PROBLEM. Phase 7.2 set a standard: no gap longer than 3 s without a
progress signal. Heartbeats existed only in the perception stage. After
A3 the reasoning stage sat silent for ~31 s while waiting on the limiter.

AUDIT RESULT. The only stage making a provider call without a heartbeat
was reasoning. Perception had heartbeats but, during a rate-limit wait,
said "still analyzing" while idle, which is a small lie. Other stages
make no provider calls (the weather call has a 10 s timeout).

DESIGN (honest, no new message type).
  - mealsight/agent/wait_status.py: a shared run_with_heartbeat that every
    provider-calling stage uses. Every 2.5 s it emits either a limiter
    COUNTDOWN ("Waiting for the rate limit, not computing: the free tier
    allows 2 requests a minute (one every 30s). About 21s to go.") when
    the call is genuinely queued, or a real in-flight description.
  - Countdown beats a one-off explanation: the UI replaces the previous
    line in place, so a changing number is visible proof of life and
    never stacks into a wall of text.
  - Message type: reused node_start with a new OPTIONAL `detail` field for
    reasoning (a client ignoring `detail` just sees a node still running,
    which is true); perception keeps ingredient_found. No new type, schema
    change is additive.
  - Interval lowered 3.0 -> 2.5 s: a 3.0 s tick lands a hair OVER a 3 s
    maximum; honouring the standard needed margin.

TWO REAL BUGS FOUND BY MEASURING (not by thinking):
  1. last_wait() is per MODEL. With a photo and a text request on the same
     model, it described whichever acquired last, so the in-flight photo
     call was labelled "rate limited". Added a per-call WaitTracker
     (ContextVar set before the task is created so the task inherits it)
     so only the call that is really queued says so. last_wait() itself is
     unchanged.
  2. HEAD-OF-LINE BLOCKING in the rate limiter. acquire() holds the model's
     lock across its whole sleep; reconcile() (which settles token counts
     after a call) took the same lock. A call that had FINISHED in a few
     seconds sat blocked behind another call's 30 s sleep: the photo
     result was ready at ~9 s but delivered at ~30 s. reconcile() is
     pure synchronous arithmetic with no await, so it needs no lock.
     After the fix the photo result arrives at 9.9 s. Total time is
     unchanged (the second call still needs its slot) but the UI is
     informed 20 s sooner. Test added: a finished call is not blocked
     behind another's wait.

RE-MEASURED over a real HTTP POST + WebSocket run: 65 messages in 64.3 s,
LONGEST GAP 2.51 s (target <= 3 s). Three runs: 62.2-64.3 s total.

FRONTEND. PipelineProgress now keeps only the LATEST detail per running
step ("Reasoning about the best fit - Waiting for the rate limit ... About
13s to go."), LiveFeed already kept one line per input type. Verified by
driving the real UI in headless Chrome over the DevTools protocol (attach
photo, type text, click, screenshots at 4/12/22/33/40/50/60/68 s): no wall
of repeated text across the minute. Cosmetic leftover (pre-existing): the
"[perceive]" prefix is still visible in live-feed lines.

NOT DONE / HONEST LIMITS: the reason node's heartbeat has no unit test of
its own (the shared helper is tested, and the live trace covers the
node); vision and text on the same model still serialise, so three calls
always cost two waits; heartbeats make the wait visible, they do not
shorten it.

A6. ADDITIONAL INTERVIEW QUESTIONS
---------------------------------------------------------------------

Q: Your first hosted run failed. What did you learn?
A: That I had removed hidden state from the tests but not from the seed
   step. The runner depended on a pantry table that only existed on my
   machine. I fixed it at both layers (runner tolerant and honest, CI
   seeding the real fixture, gate enforcing the hash) and proved it on a
   directory with no databases at all.

Q: How do you stop an outage becoming a bad benchmark?
A: A circuit breaker on final provider outcomes. The pipeline swallows
   failures into fallbacks, so scores alone can't tell "the product was
   wrong" from "the provider was down". Aborted runs are marked, never
   scored, and the gate refuses them, including as a baseline.

Q: The provider changed its limits mid-project. What did you do?
A: Measured the live headers instead of trusting my notes, updated the
   limiter, dated the comment with a re-verify warning, disabled the
   scheduled eval (keeping manual dispatch and the free per-PR matcher
   gate), measured the real product impact (11 s to 62 s), and put that in
   the README instead of hiding it.

Q: Tokens or throughput?
A: Throughput. ~426k tokens is about 4 cents, but 118 calls at one per 30
   s is an hour. My earlier cost analysis used the old limits; the
   conclusion flipped when the numbers did.

Q: How do you keep a user informed during a 60 s wait?
A: A heartbeat every 2.5 s that says what is true: a countdown when the
   call is queued behind the rate limiter, a real description when it is
   in flight. It reuses an existing message type, replaces text in place,
   and was verified against a real WebSocket trace and the real UI.

Q: Did measuring find anything thinking would not have?
A: Two bugs: a per-model wait record that mislabelled concurrent calls,
   and a limiter lock that blocked finished calls behind another call's
   30 s sleep, delaying a ready result by ~20 s.
