PHASE 10.4 STUDY NOTES: WRITING THE README AS A CLAIM-VERIFICATION EXERCISE
=====================================================================

AUDIENCE AND PURPOSE. Interview preparation. Phase 10.4 produced no new
system behavior. It produced the README, the document most readers see
and many read alone. The interesting engineering is in HOW it was written:
every number was traced to a measurement, every claim I could not trace
was cut or labelled, and the draft contained several overclaims that I
caught by checking it against the code. That process is the story.
Sections: 0 pitch, 1 what was produced, 2 method, 3 the claims I changed
and why (the core of this file), 4 design choices, 5 the three revisions,
6 mistakes, 7 principles, 8 numbers, 9 interview questions, 10 what not
to overclaim.

Companion files: mealsight/README.md, docs/EVALUATION.md, docs/CI.md,
docs/VISION_FINDINGS.md, docs/KNOWN_ISSUES.md, and the earlier notes for
10.1/10.2 and 10.3.

2. METHOD
---------------------------------------------------------------------

1. REPORT WHAT EXISTS FIRST. The brief listed docs "if present". I
   listed docs/: CI, EVALUATION, KNOWN_ISSUES, VISION_FINDINGS,
   vision_benchmark_report, vision_diagnostic_report. There is NO
   ARCHITECTURE or MCP_SERVERS document. I said so instead of linking
   documents that do not exist, and took the facts the README needed from
   the code instead (below).
2. READ BEFORE WRITING. EVALUATION.md and KNOWN_ISSUES.md in full;
   VISION_FINDINGS section 7 (the reasoning-faithfulness check) and CI.md
   for what the README cites; the other reports linked, not duplicated.
3. DERIVE FACTS FROM CODE WHERE NO DOC EXISTS:
   - MCP tool counts by listing the tool functions per server:
     recipe_engine 7, pantry_manager 8, user_intelligence 11 = 26.
   - The 11 nodes from NODE_ORDER in agent/graph.py.
   - Dependencies, Python pin (>=3.11,<3.12), the seed and server
     commands from pyproject.toml and the seeder's CLI.
4. GET REAL EXAMPLES, DON'T INVENT THEM:
   - The recommendation example is the actual result of the 64 s trace
     ("Kumpir is the best available match. The closest alternative was
     Boulangere Potatoes.").
   - The refusal example I generated by running the real pipeline on a
     case from the evaluation ("I only have 15 minutes, what can I
     make?") and pasting the actual output, including the closest recipe
     (Moussaka, match 0.4625) and its missing items.
5. TEST THE DIAGRAM. Rendered the Mermaid in headless Chrome with
   mermaid 10.9.1 and confirmed it parses and draws; reviewed the image.
6. RE-RUN THE SETUP COMMANDS. Every command in the Setup section had been
   run in this project in that form (seed from snapshot, pantry reset,
   uvicorn, vite, the checks, the eval commands). I did not re-execute a
   fresh clone end to end for the README itself, and said so.

3. THE CLAIMS I CHANGED OR REFUSED, AND WHY
---------------------------------------------------------------------

This is the high-value section. Each item is something the brief (or my
own first draft) stated that the repo could not support as written.

3.1 "Phase 8 measured 11.3 seconds."
    The brief compared 64 s to 11.3 s. 11.3 appears nowhere in the
    repo's documents or measurements, only in my own earlier notes, which
    took it from a message. An unsourced number repeated in my own notes
    does not become sourced. I omitted the comparison from the README and
    reported the omission. (I had also written it into an earlier README
    section in a previous phase; the rewrite removed it.)

3.2 "The limiter reconcile deadlock."
    The brief called the limiter bug a deadlock. What I actually found and
    fixed was head-of-line blocking: reconcile() waited on a lock that
    acquire() holds across another call's 30 s sleep; it released when the
    sleep ended, so it was a delay, not a permanent hang. The README row
    says what happened: "Rate limiter blocked finished calls behind
    another call's wait", with the effect (a result ready at ~9 s arrived
    at ~30 s). Accurate naming matters because someone may look for a
    deadlock in the code.

3.3 "About 4 cents per run, $10 allowance, pay-as-you-go disabled."
    These are facts about the account, not measurements I can repeat.
    The repo docs state them, so I kept them, but labelled them "the
    account's figure" rather than presenting them as measured.

3.4 "Nutrition 4x too high."
    EVALUATION.md records this as found by the project owner, with the
    mechanism confirmed in the code change, but I never re-measured the
    4x. The table credits it to "Evaluation work" (not a dimension) and
    describes the mechanism neutrally ("per-serving figures roughly four
    times too high").

3.5 "Reasoning made unsupported claims in 7 of 10 runs; 70%."
    Sourced: VISION_FINDINGS section 7. The same document says 6 of 10
    runs had a FALSE INGREDIENT claim specifically and 7 of 10 had any
    unsupported claim; 7/10 is the "any" count. The README says "an
    unsupported factual claim in 7". And the brief's framing "after
    restructuring" implies an improved rate: I found NO re-run of that
    10-run check after the change to data-rendered reasoning, so the
    README states that the check was not re-run and makes no claim about
    the new rate. This is the single most important honesty edit: the
    obvious sentence ("this fixed the problem") was not supported.

3.6 Overclaims in my OWN first draft, caught by checking against code:
    a. "Nodes reach data only through MCP tool calls, never the databases
       directly." I could not support it: the perception processor and the
       reasoning node call the model providers directly, and the
       perception path reads reference databases (for example synonym
       lookup) without going through MCP. I did not audit every node, so I
       deleted the sentence rather than rewording it.
    b. "Five dimensions, 150 cases, written before the results were
       known." Overclaim: Dimension 2 was re-baselined after its first run
       (20/30), and cases were added later. Rewritten to "expected answers
       were derived by hand before running the system (later corrections
       are dated and documented)", and the re-baseline is named.
    c. "Stateful dimensions run against throwaway databases." Only
       Dimensions 4 and 5 do; 1 and 2 use the real demo pantry. Changed to
       say Dimensions 4 and 5.
    d. "The provider swap was a configuration change, not a rewrite."
       The swap also exposed a scorer defect and a response-parsing
       defect (VISION_FINDINGS). Changed to "mostly configuration plus
       re-measurement (which also exposed a scorer defect and a parsing
       defect, both fixed)".
    e. "Dimension 3: no keys needed." The settings module needs the three
       environment variables at import, even for a run that makes no
       calls. Changed to "needs the three env vars set; placeholders are
       fine".

3.7 What I left out on purpose: the .env.example lists ROBOFLOW_API_KEY,
    which no backend code reads; it is not in the setup table because
    listing a key the app doesn't use would mislead a new user.

LESSON. The brief's own wording contained three claims I could not source
(11.3 s, "deadlock", an implied post-fix reasoning rate), and my draft
added five more. I only found mine by re-reading each sentence and asking
"which file proves this?" That question, asked of every sentence, is the
whole method.


---------------------------------------------------------------------
4. DESIGN CHOICES
---------------------------------------------------------------------

4.1 LEAD WITH THE FAIL, ALWAYS PAIRED WITH THE CAUSE.
The strongest thing about this project is that it measured itself and
reported failure. The first draft explained Dimension 1's failure only
beneath the evaluation table. I judged (and the owner independently asked
for) a status summary near the top: four of five dimensions pass;
Dimension 1 fails at 0.488 against 0.60 because the benchmarked vision
model was retired mid-project and the medium tier is unavailable on the
free plan; the threshold was kept, not lowered. A reader who stops after
the table now still gets the cause.

4.2 REAL OUTPUT OVER DESCRIPTION. A condensed real trace, a real
recommendation, a real refusal. Honest refusal is the common state with a
thin demo pantry (22 of 250 recipes cookable), so showing only a success
would misrepresent typical behavior.

4.3 THE BUG TABLE IS THE CENTREPIECE. Eleven rows, each with what found
it and what it would have caused. Found-by is deliberately varied and
truthful: five by evaluation dimensions, one by a manual faithfulness
check, one by the first clean-checkout CI run (MCP environment), one by a
real WebSocket trace (limiter blocking), one credited to the evaluation
work generally (nutrition). The table shows the evaluation was not the
only quality mechanism; that is more credible than claiming it caught
everything.

4.4 OPERATING COST STATED PLAINLY. 64 s per photo recommendation, almost
all rate-limit waiting after the provider's tier cut; text-only about 33
s. Called "a demo, not an interactive tool". No spin.

4.5 DIAGRAM AS MERMAID IN THE README (as requested), not an image.
First layout (left-to-right with many per-node edges) rendered but was a
tangle of long crossing lines. Rebuilt top-to-bottom with subgraph-level
edges (agent to MCP, agent to providers) and the pipeline as one row. Still
unconventional (the frontend sits low and to the right) but readable and
every label is correct. GitHub's renderer may lay it out slightly
differently.

4.6 SETUP THAT WORKS FROM A FRESH CLONE. Uses the offline snapshot seed so
it needs no live recipe API, the demo pantry reset, and the exact
commands used in CI. Prerequisites are uv (which fetches the pinned Python
3.11) and Node 20. Weather key is marked optional because the code
degrades silently without it; the Groq key is marked required because
settings refuse to start without it.

4.7 NO SCREENSHOTS YET. Two explicit placeholders (one in the intro) so
the gap is visible, not silent.

6. MISTAKES AND NEAR-MISSES
---------------------------------------------------------------------

- The five overclaims in section 3.6 were MY mistakes in a first draft,
  caught only because I audited my own text. Tell it that way: the audit
  was not hypothetical.
- My first Mermaid layout parsed fine but was unreadable. "It renders" is not "it
  communicates"; I only knew because I looked at the picture.
- A sed command with BSD syntax issues, again (macOS needs an empty
  suffix after -i); fixed by using the correct form. Same class of slip as
  in Phase 10.3.
- Editing the README after another command had already modified it
  (the rename's sed) required re-reading it before the next edit, which
  the editing tool enforced. A good guard, and an example of why file
  state assumptions go stale.
- The "11.3 seconds" figure had already leaked into a previous README
  section and into the 10.3 notes before I caught that it was unsourced.
  Repeating a number makes it feel verified.


---------------------------------------------------------------------
7. PRINCIPLES
---------------------------------------------------------------------

1. A README is a set of claims. Audit it like code.
2. Every sentence needs a file that proves it; if none does, cut or label.
3. A number repeated in a note is not a source.
4. Lead with the unflattering fact and its cause, together.
5. Show real output, including the failure mode that is common in practice.
6. Name things by what they are (blocking, not deadlock).
7. Say what you did not verify, in the same breath as what you did.
8. If the wording suggests an improvement you never measured, remove it.
9. "It renders" is not "it communicates": look at the picture.
10. Keep depth in linked docs; the README is the front door.

9. LIKELY INTERVIEW QUESTIONS
---------------------------------------------------------------------

Q: How did you write the README?
A: As an audit. I listed what docs existed (no architecture doc, so I
   derived the tool counts and node order from the code), sourced every
   figure, ran the real pipeline to capture a real recommendation and a
   real refusal, and removed or labelled any claim I couldn't trace.

Q: What did the audit catch?
A: Five overclaims in my own draft, such as "nodes reach data only through
   MCP", which the code contradicts, and "written before the results were
   known", which isn't true of a dimension I re-baselined. And three
   figures or framings in the brief I couldn't source.

Q: Why put the failing result at the top?
A: Because the strongest thing about the project is that it reports its
   own failure and explains it. A reader who sees only a FAIL in a table
   draws the wrong conclusion; the cause (the provider retired the
   benchmarked model) has to travel with it.

Q: Isn't a 64-second recommendation a problem to advertise?
A: It's the truth, and it's easy to verify by running the demo. I say it
   is a demo, not an interactive tool, and that the time is rate-limit
   waiting after the provider cut the free tier, not computation.

Q: You say reasoning was rendered from data to fix unsupported claims. Did
   it work?
A: I don't know quantitatively. The check measured 7 of 10 runs with
   unsupported claims before; I did not re-run it afterwards, so the
   README makes no claim about the new rate. The design reasoning is that
   the failures were in what the model synthesized, never in what it
   quoted, so data-rendered facts remove that failure mode, but that is a
   design argument, not a measurement.

Q: Why is the bug table credible?
A: It names who found each bug and it is varied: evaluation dimensions,
   a manual check, a CI run and a WebSocket trace. It doesn't claim the
   evaluation found everything.

Q: What would you add?
A: Screenshots or a short recording, a re-run of the faithfulness check
   against the current reasoning, an architecture document (none exists),
   and a measured fresh-clone setup run by someone other than me.

10. WHAT NOT TO OVERCLAIM
---------------------------------------------------------------------

- The README makes no claim that data-rendered reasoning reduced the
  unsupported-claim rate; that was not re-measured.
- "About 4 cents per run" and the $10 allowance are the account's figures,
  not measurements I can reproduce.
- The 4x nutrition error was recorded by the project owner; I confirmed
  the mechanism in the code change but did not re-measure the magnitude.
- The diagram renders with mermaid 10.9.1 in headless Chrome; GitHub's
  renderer may differ. It was reviewed once as an image.
- Setup commands were each run in this project, but I did not do a
  complete fresh-clone run of the README's Setup section as written.
- The 64 s figure is one workflow (photo plus text) over three runs on
  one account, not a distribution.
- There is no ARCHITECTURE or MCP_SERVERS document; the README's
  architecture facts come from the code, not from a maintained doc.
- Screenshots are placeholders. No screenshot or recording exists in the
  README yet.
