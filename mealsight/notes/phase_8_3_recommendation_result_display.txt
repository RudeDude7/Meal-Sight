1. THE GAP: SUBSTITUTION DATA EXISTED IN MEMORY AND NOWHERE ELSE
=============================================================
Reading generate_output.py, reason.py, match_rank.py's own models.py,
cook.py, and the recommend router's _serialize_result/_RESULT_FIELDS
directly (not the frontend's already-existing types, which turned out
to already be correct against every OTHER shape) turned up one real
discrepancy: generate_output._build_available_response calls
find_substitutions for whatever's still missing and gets back real
SubstitutionResult objects (ingredient, reason, suggestions — each with
substitute/ratio/flavor_impact/notes — excluded_count) — but the
function's own returned `update` dict never included them. They were
computed ONLY to be woven into final_response's own prose ("If you're
missing something, try: X for Y (Z flavor impact)"), then discarded.
_RESULT_FIELDS never listed a "substitutions" key because there was
never a state key for it to read. No REST endpoint anywhere in this API
returns match/substitution data independently either — GET /api/recipes
/{id} returns RecipeDetail (no matching info at all), and there's no
"match this recipe against my pantry" endpoint exposed at the HTTP
layer. The result: everything else the task asked for (missing items
WITH importance, in particular) already had a real, structured path —
grocery_list's own items already carry importance/is_staple/verify_note,
built directly from missing_items — but ratio/flavor_impact had no wire
representation at all.

Presented this finding to the user directly rather than picking
silently among the three real options (add a backend field / parse
prose out of final_response / drop the display entirely) — this is
exactly the kind of decision only the user can make when a "frozen"
backend needs the frozen boundary tested. The user chose the additive
field, matching the precedent matched_ingredients itself already set
(that field's own comment: flattened to top-level "so a client has one
obvious, stable field to read... from").

3. WHY CookableResult MAKES A SECOND, SEPARATE FETCH — get_recipe, NOT
   JUST scaled_recipe
=============================================================
scaled_recipe (ScaledRecipe, from scale_recipe) carries name, cook_time,
target_servings, and scaled ingredients — but the pydantic model itself
has NO cuisine field, no dietary_tags field, and critically no steps
field at all. Those three only exist on RecipeDetail (get_recipe's own
return shape), which generate_output DOES fetch internally but never
adds to the state update dict either (unlike scaled_recipe/grocery_list/
nutrition_info/matched_ingredients, `detail` itself never left the
node). Rather than treating this as a second gap needing a second
backend field, CookableResult calls the ALREADY-EXISTING GET /api/
recipes/{id} (src/api/recipes.ts's own getRecipe, built and typed
correctly in an earlier phase, previously used only by recipe-browsing
pages that don't exist yet) — keyed on result.recipe_id, which
_serialize_result already flattens onto the top-level result
specifically, per its own comment, so a client has one obvious place to
read it from. This is real data through a real, already-shipped
endpoint, not a guess and not a new backend surface.

The fetch is genuinely optional to the view's own correctness: cuisine,
dietary marks, and steps degrade to "unknown"/"loading" text rather than
blocking anything else on the page from rendering, and a failed fetch
shows a plain "Couldn't load the steps" line rather than a blank space
or a thrown error.


4. HAVE VS. MISSING: A NAME-SET DIFF BETWEEN TWO FIELDS THAT ALREADY
   EXIST FOR EXACTLY THIS PURPOSE
=============================================================
matched_ingredients' own doc comment (state.py) already says what it's
for: "the chosen recipe's own matched_items... cross-referenced against
scaled_recipe's own ingredients for a quantity_display/unit — the
'what's needed, and how much, for what you already have' list." Reading
that literally: an ingredient in scaled_recipe.ingredients whose
(lowercased) name appears in matched_ingredients is "have"; every other
scaled ingredient is "missing" — no new data needed, no separate call,
just the diff this pairing was already built to support. Each scaled
ingredient already carries its own importance field too, so "missing
with importance level" (task item 4) reads directly off scaled_recipe,
without needing to cross-reference grocery_list for that specific piece
at all — grocery_list is used instead, and separately, for its own
distinct purpose (the store-section-grouped shopping list with staple
flags).

8. VERIFICATION, PART TWO: A REAL PANTRY, A REAL BACKEND, AND WHY THE
   FIRST THREE RUNS ALL CAME BACK "NO MATCH"
=============================================================
Started the real backend (uvicorn, port 8000) against the real,
already-populated SQLite databases left over from earlier sessions'
live verification (24 real pantry items: chicken breast, chicken thigh,
corn tortilla, cream cheese, enchilada sauce, monterey jack cheese, and
others — the literal ingredients the "Chicken Enchilada Casserole"
example has been built around throughout this whole project) and the
real Vite dev server, then drove actual recommendation runs through the
real rendered UI via puppeteer-core, not by fabricating a result object
to render against.

The first three real runs — plain text mentioning chicken and
tortillas, then an explicit "Mexican dinner... 45 minutes or less"
request — all came back "No match this time," and NOT because the
frontend or the new substitutions field were broken: direct inspection
of the real processing_trace.relaxations and a direct GET /api/recipes/
search?cuisine=Mexican call (which DID return five real Mexican recipes,
including Chicken Enchilada Casserole itself, id 52765) confirmed two
real, pre-existing BACKEND behaviors, reported here rather than quietly
worked around:

  (a) mealsight.agent.nodes.search_recipes relaxes cuisine FIRST, cook-
      time SECOND, meal-type LAST (grep-confirmed against the actual
      relaxation messages, not assumed from the docstring). get_context's
      own inferred meal_type is one of breakfast/lunch/dinner/snack; the
      real recipe corpus's own meal_type field is a completely different
      vocabulary (main/dessert/side/etc., inherited from TheMealDB's own
      categories) that never intersects with it at all. The practical
      effect: the meal-type filter excludes literally everything on
      essentially every real request, but because cuisine relaxes away
      BEFORE meal-type does, a stated cuisine preference is discarded
      before it ever gets the chance to matter — the search that
      finally succeeds has neither constraint left, and returns
      whatever's alphabetically first in an unrelated, unfiltered
      results page.

  (b) Once every constraint is relaxed away, search_recipes' own default
      ordering is NOT related to the free-text description's own
      mentioned ingredients at all (there is no "contains these
      ingredients" filter anywhere in this API) — match_rank only scores
      whatever candidate set search_recipes happens to hand it, so a
      request explicitly naming chicken and tortillas can genuinely
      surface Bubble & Squeak and Apple Frangipan Tart as its top
      candidates, with the real, correct pantry (which has never seen
      those ingredients) correctly scoring both at match_score 0.0-0.03.

Neither of these is a frontend bug, and neither was touched — both are
pre-existing backend search/context behavior, out of this phase's own
scope (a frozen backend, minus the one field this phase was explicitly
authorized to add), reported plainly rather than silently worked around
or quietly attributed to "flaky data."

10. A SECOND FINDING, ALSO REPORTED RATHER THAN SILENTLY WORKED AROUND:
    A FIXED BOTTOM TAB BAR CAN STEAL A CLICK AT NARROW WIDTHS
=============================================================
The first attempt at the 375px screenshot submitted the recommendation
form directly at 375px width and never completed — the captured
screenshot showed the app had navigated to /grocery-list instead,
despite the script explicitly clicking the "Get a recommendation"
button by its own text content. Diagnosed rather than dismissed as
flakiness: NavShell's own BottomTabBar is `fixed inset-x-0 bottom-0
z-20`, and at 375px width the input form's own submit button can end up
positioned, after the page scrolls to bring it into view, at a screen
coordinate the fixed tab bar physically occupies — Puppeteer's own
.click() dispatches to whatever element is actually topmost at that
coordinate, which was the tab bar's own "Grocery List" link in this
case, not the button underneath it. Worked around for THIS phase's own
verification by submitting at desktop width and resizing to 375px only
after the result had already rendered (a real, correct screenshot of a
genuinely narrow layout, just reached by a different sequencing) — but
the underlying overlap is a real layout issue in the shell built during
phase 8.2(b), out of this phase's own scope to fix, reported here so a
future session doesn't have to rediscover it from scratch.


11. DECISIONS AND ALTERNATIVES REJECTED
=============================================================
Parsing substitution ratio/flavor_impact out of final_response's own
prose versus adding a small, additive backend field
    Presented to the user rather than picked silently, since it meant
    touching a backend explicitly described as frozen. The user chose
    the additive field. Text-parsing was rejected as the fallback this
    project has rejected in every prior similar moment: it would have
    meant re-deriving structured data from a string whose ONLY contract
    is being readable prose, with no guarantee its exact wording (a
    format string in _format_available_response) stays stable — fragile
    by construction, and against this whole project's own "don't
    guess/fake structured data" discipline.

Fetching RecipeDetail via a new, dedicated endpoint versus reusing the
already-existing GET /api/recipes/{id}
    Rejected adding anything: getRecipe already existed, already
    correctly typed, already unused by any shipped page. Cuisine,
    dietary_tags, and steps were sitting behind an endpoint this project
    had already built and verified in an earlier phase; reaching for it
    was the same "real data through a real, already-shipped path" choice
    this project makes whenever the option exists, rather than treating
    "the frontend has no steps" as a second backend gap requiring a
    second field.

Deriving have-vs-missing ingredients from grocery_list versus diffing
scaled_recipe against matched_ingredients directly
    Rejected reading it off grocery_list: that field is generate_output's
    OWN missing-ingredients list turned into a shopping list, but it's
    absent entirely on a 100%-match recipe (nothing to build a list
    from) and doesn't carry the full scaled ingredient set (quantity_
    display, unit) needed to render the "have" side at all. matched_
    ingredients' own doc comment already states its purpose is exactly
    this cross-reference; using it directly needed no new data and
    matches what it was already built for.

Screenshotting the 375px case by submitting fresh at that width versus
resizing after a desktop-width run completed
    Rejected repeatedly forcing the narrow-width submission once the
    fixed-tab-bar click interception was diagnosed (section 10): forcing
    it would have meant either fighting a real, separate layout bug
    that belongs to a different phase, or picking an artificial click
    coordinate that doesn't reflect how a real user would actually tap
    the button on a real phone. Resizing after completion still produces
    a genuine, unstaged 375px render of the real result — the ONLY thing
    that changed was avoiding a known-broken click path irrelevant to
    what this screenshot needed to prove.


12. GLOSSARY
=============================================================
RecommendationResultView
    The dispatcher (frontend/src/components/recommend/result/
    RecommendationResultView.tsx) — branches on top_recommendation.
    available, nothing else, to choose CookableResult vs. NoCookableResult.

CookableResult
    Renders the RecipeTicket header (RecipeIcon, DietMarks, match score,
    cookable Stamp), the ingredients have/missing split, steps, and
    composes NutritionPanel/ReasoningPanel/MissingAndSubstitutions/
    CookThis underneath. The one component that makes the supplementary
    GET /api/recipes/{id} call described in section 3.

NutritionPanel
    The Partial/caveat pattern's own home — signal-info Stamp plus the
    backend's real coverage_note, triggered at coverage_pct <=
    MIN_COVERAGE_PCT_FOR_TAGS (80.0, matched exactly against recipe_
    engine/nutrition.py's own constant, not re-derived independently).

ReasoningPanel
    Renders all six *_reasoning dimensions unconditionally, dimming
    (not hiding) any the model marked not-applicable; falls back to
    overall_summary alone when reasoning itself is absent (the two
    fallback-decision paths in reason.py).

MissingAndSubstitutions
    Missing ingredients (name + importance, diffed from scaled_recipe
    against matched_ingredients), this phase's own new substitutions
    field (ratio/flavor_impact), and the grocery_list grouped by real
    store section with staple verify_note text — three independent
    optional sections, each rendering only when its own data exists.

CookThis
    The Cook-confirmation form and its own Success-pattern result view;
    treats idempotent_replay and a non-null pantry_deduction_error as
    variations WITHIN the success view, never as a different pattern.

substitutions (RecommendationResult field)
    This phase's own new, additive wire field — one SubstitutionResult
    per still-missing ingredient that had a real find_substitutions
    lookup succeed. Absent on the no-cookable path, and absent on the
    cookable path whenever every substitution lookup came back empty.


13. INTERVIEW TALKING POINTS
=============================================================
Q: You found that a stated cuisine preference basically never survives
to matter in the real system. Why not just fix the relaxation order
while you were already in there?

    Because it wasn't what was asked, and it isn't a small, additive,
    precedent-matching change the way substitutions was. Reordering
    relaxation (or reconciling the meal_type vocabularies) touches
    search_recipes' own behavior for every single recommendation this
    system will ever produce, changes the SHAPE of when a run succeeds
    or fails, and has its own test surface this phase never audited. The
    substitutions field, by contrast, was additive, provably backward-
    compatible (every existing test still passed unmodified), and
    directly authorized by the user after being presented as a real
    gap. Reporting the meal_type finding clearly, rather than either
    silently ignoring it or silently fixing it, is what keeps the "the
    backend is frozen except for what's explicitly agreed" boundary
    meaningful.

Q: How do you know the "No match this time" result you screenshotted
was a real system behavior and not, say, the new RecommendationResultView
component failing to parse a result it didn't expect?

    Because I checked the raw JSON directly, not just the rendered page:
    curl against GET /api/recommend/{id} showed the exact same
    top_recommendation.explanation and grocery_list.sections the UI
    rendered, and processing_trace.relaxations showed the real messages
    search_recipes actually streamed ("Dropping the Mexican cuisine
    preference...", "dropping the lunch meal-type filter..."). If the
    component had been silently swallowing or misreading the result, the
    rendered explanation text wouldn't have matched the raw JSON's own
    explanation field character-for-character, which it did.

Q: The Cook This flow you verified didn't include a rating. Why not
just click a rating button too, to prove the preference-change text
renders?

    I could have, and chose not to invent a rating just to force that
    one text line to appear during this pass — the honest state of this
    verification is that preferenceChangeText's own logic (comparing
    preferences_before/after cuisine_preferences for the recipe's own
    cuisine) is implemented and typed against the real UserProfile
    shape, but only the no-rating branch was actually exercised live
    this session. I said that directly rather than either skipping the
    distinction or overstating what was actually confirmed.

Q: Why does CookableResult treat a failed getRecipe fetch as "show
'Couldn't load the steps'" rather than falling back to some default
step text or hiding the whole Steps section?

    Because there's no honest default step text to fall back to — this
    system's own established rule (RecipeIcon, DietMarks, the empty-
    state illustrations, all from earlier phases) is "don't guess, don't
    fake it" whenever real data isn't available. Hiding the section
    entirely would silently under-deliver without saying why; inventing
    placeholder steps would be actively dishonest. A plain, visible
    "couldn't load" message is the same pattern this whole project
    already uses everywhere else data might be genuinely unavailable.
