1. DEFECT 1's FIX: complete_json NEVER TOLD THE MODEL THE SHAPE IT
   WANTED
=============================================================
providers/mistral.py's complete_json validated a response against a
pydantic schema but never serialized that schema into the request —
every caller had to hand-spell the JSON field names in its own prompt
text, discovered the hard way in Phase 6.3 when reason.py's first real
run omitted that block and failed validation twice before falling back.

Fixed at the provider layer, not caller by caller: two new module-level
functions, _describe_type and _describe_schema, walk a pydantic
BaseModel's own model_fields (recursing into any nested BaseModel field,
handling Optional/Union via both typing.Union and the newer
types.UnionType, and list[X]) into a compact {"field": type, ...}
string — deliberately NOT a full JSON Schema dump (no title, no
description, no $defs), since these prompts run against a 375K TPM
budget and a caller only needs to know field NAMES and rough SHAPE, not
every constraint a real JSON Schema would carry. complete_json now
embeds this description in every request unconditionally, so a caller
cannot forget it the way reason.py's first version did.

Checked every existing caller for now-duplicated instructions rather
than assuming none existed:
  - agent/nodes/reason.py's SYSTEM_PROMPT hand-wrote the exact JSON
    skeleton this defect describes (six DimensionReasoning objects, key
    by key) — this WAS the literal Phase 6.3 workaround. Removed the
    structural block entirely, keeping only genuinely behavioral
    guidance (favor can_cook, never invent an id not offered, all six
    *_reasoning fields required even when applies is false).
  - perception/prompt.py's build_extraction_prompt does NOT hand-write
    a JSON skeleton at all (only a prose "Fields to extract" list
    conveying per-field MEANING, not structure) — left unchanged, since
    trimming it would remove real domain guidance the compact schema
    block can't provide, not a duplicate.
  - VISION_PERCEPTION_PROMPT never goes through complete_json at all
    (uses analyze_image directly, parsed by processor.py's own
    _parse_raw_response) — confirmed unaffected by this defect.

3 new unit tests lock in the compact format (asserting no "$defs" or
"title" leak in, and that a nested BaseModel field recurses correctly)
and confirm a caller whose own prompt never names a single field still
produces a request containing the real field names.


2. DEFECT 2's FIX: A CATCH-ALL, PLUS AN ANTI-HALLUCINATION INSTRUCTION
   — AND A REAL SECOND-ORDER REGRESSION THE FIRST FIX CAUSED
=============================================================
Phase 5.3's own run had dropped text_05's "no seafood" and text_09's
"not too spicy" entirely — not misplaced, absent from every field
including additional_context — because build_extraction_prompt had no
instruction covering a stated constraint that doesn't map cleanly onto
a schema field. The same run also invented "tired" in text_09's
mood_or_preference from a user who never said it.

Read the real ground truth in test_data/text/text_inputs.json before
assuming the task's own literal framing ("fall back to
additional_context") was the complete fix: text_05 and text_09 both
expect their constraint IN avoid_ingredients ("seafood", "excess
spice"), not additional_context. So the real fix had two parts: (a)
teach the model that avoid_ingredients can hold broader avoid-
categories, not just single named items, and (b) keep the
additional_context catch-all as a genuine secondary safety net for
constraints that don't fit ANY field, not as the primary destination
for these two cases specifically. Also added an explicit instruction
that wanting something easy/quick/on-hand is never evidence of
tiredness or any other unstated emotional state.

THE REGRESSION THIS CAUSED, FOUND BY RE-RUNNING THE FULL CORPUS RATHER
THAN JUST THE TWO NAMED CASES: memo_11 ("nothing too heavy tonight")
started producing avoid_ingredients: ["heavy food"] instead of the
correct empty list plus a mood_or_preference note — the broadened
wording for avoid_ingredients ("ingredient-like categories/qualities...
'not too spicy' belongs here as 'excess spice'") over-generalized to a
whole-meal-character complaint that isn't really about a specific
ingredient dimension at all. Fixed by narrowing the boundary explicitly
in the prompt: avoid_ingredients only covers something traceable to a
specific ingredient, additive, or seasoning dimension (spice/heat
level, sweetness, saltiness, a named allergen); a statement about how
the MEAL AS A WHOLE should feel ("not too heavy", "something light")
is a mood, not an ingredient to avoid, even though both are phrased as
a "not too X" complaint. Re-verified memo_11 directly after this
narrowing: avoid_ingredients back to [], mood_or_preference correctly
now says "not too heavy" instead of leaking into the wrong field.

This is the same lesson Phase 2.2 and Phase 9.1 both already
independently arrived at in this project: a fix aimed at one named
failure case, verified only against that case, can look complete while
quietly breaking an adjacent one — the full-corpus re-run, not just the
two cases the task named by id, is what actually caught it.

5. DEFECT 4's FIX: A 15-RECIPE INVESTIGATION FIRST, A MINIMAL
   TERM-LIST EXTENSION SECOND
=============================================================
KNOWN_ISSUES.md #2 named the gap directly (assign_importances only
reaches critical via title-match or PROTEIN_TERMS, so potato in Spanish
Tortilla is merely important) and explicitly asked NOT to speculatively
expand term lists without first confirming the error rate justifies it.

Sampled 15 real recipes whose names contain a non-protein defining
ingredient, including the two examples KNOWN_ISSUES.md itself already
named (Fettucine alfredo, Baingan Bharta). Manually verified every
flagged case against each recipe's real stored ingredients (via direct
sqlite3 queries, not the sample script's own crude string matching) to
separate genuine misses from artifacts and from legitimately-correct
existing behavior:
  - 2 samples (Salmon Prawn Risotto, Jerk chicken with rice & peas) are
    NOT real misses — their titles genuinely name a protein, and
    title-match already correctly wins.
  - Bread and Butter Pudding is a minor pre-existing tie-break, not a
    Defect-4 case (both "bread" and "butter" are literal title
    substrings; title-match already fires, just resolves a two-way tie
    by ingredient order).
  - 9 GENUINE MISSES, the material rate that justified a real fix:
    Spanish Tortilla (Eggs won over Potatoes), Mediterranean Pasta
    Salad (tuna won over "farfalle" — no substring "pasta" at all),
    Vegetable Shepherds Pie (Brown Lentils won over Potatoes, since
    lentils is itself a PROTEIN_TERMS entry), Laksa King Prawn Noodles
    (fish sauce won over "rice noodles"), Rappie Pie (Chicken Stock won
    over Potatoes), Pierogi (Eggs won over Potatoes, a real filling
    ingredient), Baingan Bharta (nothing became critical — real
    ingredient is "Aubergine", not "Eggplant"), Fettucine alfredo
    (nothing became critical — real ingredient is "Fettuccine", no
    substring "pasta"), Squash linguine (nothing became critical —
    "Butternut Squash" / "Linguine Pasta", neither a PROTEIN_TERMS
    entry).

Fix: a new DEFINING_STAPLE_TERMS frozenset — potato, noodle, pasta,
farfalle, fettuccine, squash, aubergine — every term traced to one of
the 9 genuine misses, not speculatively added. Inserted as a NEW middle
tier BETWEEN title-match and the protein-term fallback, not appended
after it: the investigation showed the actual failure mode was the
protein fallback firing on a minor background ingredient (an egg in
pierogi dough, a splash of chicken stock, a lentil filler) before the
dish's own real defining staple ever got a chance, so the ordering
itself — not just the term list — is what fixes the observed pattern.

Re-sampled after the fix: all 9 genuine misses resolved, zero
regressions to the already-correct cases (title-match still wins
outright for Salmon Prawn Risotto and Jerk chicken; Boulangère
Potatoes, Breakfast Potatoes, Chicken Couscous unaffected). 5 new
regression tests added, including one that explicitly asserts the new
tier never fires when title-match already found something.


6. DEFECT 5's FIX: THE ACTUAL TRIGGER WAS NARROWER THAN THE TASK'S
   OWN FRAMING SUGGESTED
=============================================================
The task described the trigger as "the soft keyboard or a growing
textarea reflows the page." Neither half of that framing turned out to
be quite right: TextInput.tsx's textarea has a fixed rows={3} and never
grows at all, and three straight reproduction attempts at a full
375x700 viewport (typing text first, then clicking; a fresh page with a
direct .click(); a fresh page with Puppeteer's own auto-scroll-into-
view) all failed to reproduce anything — the button's native scroll
landed it safely clear of the fixed BottomTabBar every time at that
viewport height.

The actual trigger, found by simulating a REAL soft keyboard's
footprint rather than a generic click: squeezing the Puppeteer viewport
to 375x320 (a real keyboard can consume 40-50% of visual viewport
height) and using textarea.focus() specifically (not .click()) to
trigger the browser's own native focus-scroll-into-view behavior.
document.elementFromPoint at the submit button's own center then
resolved to the tab bar's "Grocery List" link, not the button, and a
real click navigated to /grocery-list instead of submitting —  an
exact, mechanistic reproduction.

DIAGNOSIS: clearance, not stacking context (the tab bar's z-index and
fixed positioning are working exactly as intended) and not pointer-
events (the tab bar SHOULD stay clickable everywhere it's visually
present — disabling that would break real tab-bar taps). The page
scrolls at the document/html level with no nested overflow container,
so a native focus-triggered scrollIntoView has no idea the fixed 56px
tab bar visually covers the bottom of the viewport.

THE FIRST FIX ATTEMPT WAS INSUFFICIENT, FOUND BY RE-RUNNING THE SAME
REPRO SCRIPT AFTER APPLYING IT: scroll-padding-bottom: 56px (exactly
the tab bar's own height) on html, scoped below the md breakpoint,
still left the button's rect overlapping the bar's by ~31px after the
fix. Root cause of the shortfall: scroll-padding only guarantees
clearance for whatever element is the actual scroll-into-view TARGET
(the focused textarea) — it says nothing about interactive elements
sitting further down the page, like this page's own submit button,
measured at ~91px below the textarea. Widened to 160px (bar height +
realistic field-to-action-button clearance, rounded up), re-verified
with the identical repro script: button rect fully clear of the bar
rect, elementFromPoint resolves to the real button, and a real click no
longer navigates away. Confirmed visually with a screenshot at the
squeezed viewport showing genuine daylight between the button and the
tab bar.

8. DECISIONS AND ALTERNATIVES REJECTED
=============================================================
Trimming perception/prompt.py's own field-description prose when
adding the schema block to complete_json, versus leaving it alone
    Rejected trimming: build_extraction_prompt's "Fields to extract"
    list conveys per-field MEANING (what counts as a dietary
    restriction vs an avoid-ingredient) that the new compact schema
    block, by design, cannot — the block only tells the model field
    names and rough shape, not domain semantics. Removing it would have
    been cutting real, non-duplicated guidance to chase a structural
    similarity that isn't actually a duplication.

A pure additional_context catch-all for text_05/text_09 (the task's own
literal framing) versus also broadening avoid_ingredients itself
    Rejected the pure catch-all: the real ground truth in
    text_inputs.json expects both constraints IN avoid_ingredients, not
    additional_context — implementing only the task's literal
    instruction would have produced code that passes a superficial
    reading of the task but fails the actual scored test data.
    additional_context was kept as a genuine secondary safety net, not
    the primary fix.

Leaving the broadened avoid_ingredients wording as-is after confirming
text_05/text_09 versus re-running the FULL corpus before declaring the
fix complete
    Rejected declaring it complete early: the two named cases alone
    would have looked fixed while memo_11 silently regressed. Only the
    full 30-case re-run surfaced this, consistent with this whole
    project's repeated lesson (Phase 2.2, Phase 9.1) that a fix
    verified only against its own named failure case can hide an
    adjacent one.

Diluting DEFINING_STAPLE_TERMS to catch every plausible starch versus
scoping it strictly to terms the 15-recipe investigation actually
produced
    Rejected the broader list: KNOWN_ISSUES.md #2 explicitly warned
    against speculative expansion, and every term actually used here
    traces to a real, verified miss in the sample rather than a guess
    at what might also matter.

Appending the new staple-term tier AFTER the protein-term fallback
versus inserting it BEFORE
    Rejected appending it after: the investigation showed the failure
    mode was specifically the protein fallback winning ahead of a real
    staple that happened to sit later in the ingredient list (egg in
    dough, stock, a lentil filler) — appending the new tier after an
    already-winning fallback would never let it fire in exactly the
    cases it exists to fix.

scroll-padding-bottom at exactly the tab bar's own 56px height versus a
wider, empirically-verified value
    Rejected the exact-height value: it looked like the obviously
    "correct" number but the repro script proved it insufficient —
    scroll-padding only protects the actual scroll target (the
    textarea), not the button positioned further down the page. 160px,
    verified against the real measured field-to-button distance plus
    the bar height, was the value that actually closed the gap rather
    than the value that looked most principled on paper.


9. GLOSSARY
=============================================================
_describe_schema / _describe_type (providers/mistral.py)
    The compact, recursive {"field": type, ...} renderer complete_json
    now embeds in every request — deliberately not a full JSON Schema
    dump, just enough for a model to know field names and rough shape.

DEFINING_STAPLE_TERMS (seed/recipe_parsing.py)
    The new middle importance tier, checked between title-match and
    PROTEIN_TERMS — a small, evidence-traced set of non-protein
    starch/vegetable terms (potato, noodle, pasta, farfalle, fettuccine,
    squash, aubergine) that can reach critical when nothing in the
    title matches.

_matches_any_term_whole_word (seed/recipe_parsing.py)
    The shared whole-word-with-pluralization-tolerance regex matcher —
    now used by both assign_importances (its original Phase 2.2 home)
    and _any_term_matches / _has_unsafe_gluten_ingredient (this phase's
    fix).

scroll-padding-bottom (frontend/src/index.css)
    Reserves space at the bottom of the document's own scrollport so a
    native scroll-into-view (focus, anchor navigation) doesn't position
    its target — or, empirically, elements just past its target —
    behind the fixed BottomTabBar. Set to 160px below md, 0 at md and
    above where the tab bar doesn't exist.


10. INTERVIEW TALKING POINTS
=============================================================
Q: The task said all five of these were logged in KNOWN_ISSUES.md.
Why does your report say only two actually were?

    Because checking is cheaper than assuming, and the doc is short
    enough to read directly before starting. Only EGG_TERMS substring
    matching and the non-protein-staple gap are actually in it; the
    other three were logged in earlier phases' own notes files (6.3,
    5.3) or nowhere formally at all (the mobile tab bar issue). I said
    so up front rather than let the task's framing stand uncorrected,
    then fixed all five anyway since the task gave full specifics for
    each regardless of where they were originally recorded.

Q: You fixed the avoid_ingredients wording, confirmed the two named
cases worked, and could have stopped there. Why the extra full-corpus
run?

    Because "confirmed the two named cases" and "confirmed nothing
    regressed" are different claims, and the task asked for both. This
    project has hit the same shape of problem twice before (Phase 2.2's
    peanut-pluralization regression, Phase 9.1's own search-defect
    ordering) — a fix that looks complete against its own trigger case
    can break an adjacent one that nobody thought to re-check. The
    30-case re-run is what actually found memo_11's regression; without
    it, "not too heavy" would have started silently mis-filing into
    avoid_ingredients in production.

Q: For the mobile tab bar fix, why 160px specifically instead of just
the tab bar's own 56px height?

    Because I tried 56px first, expecting it to be sufficient since
    that's literally the overlay's own footprint, and the repro script
    proved it wasn't — the button still overlapped the bar by about
    31px afterward. scroll-padding-bottom only guarantees clearance for
    whatever element is the actual target of a scroll-into-view call,
    which here is the textarea being focused, not the submit button
    sitting further down the page. I measured the real distance between
    them (about 91px) and set the padding to bar height plus that
    distance, then re-ran the exact same repro to confirm the overlap
    was actually gone rather than assuming a rounder number would work.

Q: Why insert the new staple-ingredient tier between title-match and
protein-match instead of just adding it as another check somewhere?

    Because the investigation showed WHERE in the existing order the
    bug actually lived: the protein-term fallback was winning on a
    minor background ingredient before a real defining staple later in
    the list ever got evaluated. If I'd appended the new tier after
    the protein fallback instead of before it, it would never fire in
    the exact cases — Pierogi's Eggs, Rappie Pie's Chicken Stock — that
    motivated adding it in the first place. The fix isn't really "a new
    term list," it's "the right term list checked at the right point in
    the existing precedence order."
