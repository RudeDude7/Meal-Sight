PHASE 9.5 STUDY NOTES: MULTI-DAY MEAL PLANNING — THE ORIGINAL SPEC'S
MOST AMBITIOUS TOOL, BUILT WITHOUT THE CROSS-DATABASE SHORTCUT THAT
ORIGINALLY DEFINED IT
=============================================================

The original spec placed suggest_meal_plan inside User Intelligence,
doing cross-database queries straight into pantry and recipes — a real
violation of the one rule every other server in this system already
respects (each server owns its own data; cross-server composition is
the agent's job, never a single tool's). This phase was explicitly
told not to replicate that, and to report where planning logic
actually belongs before writing anything. What follows is that
decision, the deterministic algorithm built to satisfy it, and the
first phase in this project's history to ship a five-bullet
combinatorial-optimization feature with zero new server-side tools.

Files added: backend/mealsight/{planning/{__init__.py,models.py,
scheduler.py},agent/meal_planner.py,api/routers/meal_plan.py},
backend/tests/{test_planning/test_scheduler.py,test_agent/
test_meal_planner.py}, frontend/src/{types/mealPlan.ts,api/mealPlan.ts,
pages/MealPlan.tsx}. Files edited: backend/mealsight/api/app.py (router
registration only), frontend/src/{App.tsx,components/layout/
{NavShell.tsx,NavIcons.tsx}}, backend/tests/test_api/test_app.py (two

1. THE ARCHITECTURE DECISION, REPORTED BEFORE ANY CODE WAS WRITTEN
=============================================================
Read every one of the 24 existing tools' own docstrings across all
three servers before designing anything — not assumed, checked:
search_recipes/get_recipe/match_ingredients/scale_recipe/
calculate_nutrition (recipe_engine), get_pantry/flag_expiring/
create_grocery_list (pantry_manager), check_repetition/get_user_
profile (user_intelligence). Every piece of data multi-day planning
needs already exists behind one of these. That absence of any real gap
is itself the finding this phase reports: cross-server composition
genuinely is satisfiable as "the agent's job" without inventing a new
cross-cutting tool to paper over a missing capability — if a gap HAD
existed, that would have been the signal a new tool was actually
warranted; none did.

The feature splits into two new pieces on that basis:
    mealsight/planning/  — a pure, deterministic scheduler (models.py +
        scheduler.py). No mealsight.db import, no MCP client, no LLM —
        enforced by mealsight/planning/__init__.py's own module
        docstring as an explicit rule, not just a description, and
        verified true by mypy --strict/ruff finding nothing to
        complain about when this package was checked in isolation.
    mealsight/agent/meal_planner.py — the ONE place in this whole
        feature allowed to reach across recipe_engine/pantry_manager/
        user_intelligence, mirroring mealsight.agent.runner.
        run_recommendation's own shape exactly (same MCPClientManager-
        reuse contract, same trace_id binding, same "pass an
        already-started manager or get a fresh owned one" pattern) —
        not a new LangGraph node, since multi-day planning has no
        photo/voice/text perception step and no single LLM-judged
        choice among a short list; bolting it onto the existing
        eleven-node sequential graph would have forced a fundamentally
        different operation into a shape built for a different one.


2. THE PLANNING PROBLEM: A GREEDY ALGORITHM, REPORTED WITH ITS REAL
   COMPLEXITY AND ITS REAL LIMITS
=============================================================
build_schedule (mealsight/planning/scheduler.py) assigns one candidate
per day, greedily, in day order — never a search over all C(P, days)
day combinations, which the task's own instruction named directly as
the thing NOT to build (genuinely exponential, the same category of
overreach as asking an LLM to schedule five days). At each day:

Hard filters, in order: no exact-recipe repeat this plan; never let one
protein_type exceed settings.max_same_protein_per_week (a real hard
cap — the only way to GUARANTEE it, not just usually hit it); never
repeat the immediately preceding day's cuisine, UNLESS that would leave
zero eligible candidates for the day, in which case ONLY that one
softer variety goal relaxes (recorded honestly via DayAssignment.
cuisine_repeat_forced) — dietary restrictions and the protein cap never
relax this way.

Scoring (same dominant-term shape as agent/nodes/match_rank.py's own
composite — ingredient match dominant, secondary signals layered on,
critical-missing an overriding penalty bigger than every positive term
combined) plus three genuinely new terms match_rank never needed: a
day-position-DECAYED freshness bonus (day 0 gets the full bonus, the
last day gets 1/days of it — the literal mechanism behind "an expiring
ingredient should land early, not on day five," not a separate rule
bolted on afterward), a cross-day overlap bonus (rewards a candidate
whose to-be-bought ingredients overlap with what an earlier day already
commits to buying — this is the classic greedy set-cover heuristic's
own marginal-gain shape, with that heuristic's well-known, HONESTLY
CITED property: within a ln(n) factor of optimal, never claimed to
find the true optimum), and a repetition penalty pulled straight from
check_repetition rather than recomputed — the task's own explicit
"reuse check_repetition rather than reimplementing" instruction,
applied literally.

COMPLEXITY, stated plainly rather than hand-waved: P = candidate pool
size (bounded to MAX_PLANNING_CANDIDATES=40 by the orchestration layer,
not the scheduler), D = days. O(D × P) score evaluations, each O(1)
beyond a small set intersection bounded by one recipe's own ingredient
count. No recursion, no backtracking. All the real wall-clock cost in
a request is the I/O gathering candidates (one match_ingredients call
per candidate) BEFORE build_schedule is ever called — confirmed
directly by the real verification run's own timing (section 6): the
whole five-day plan, from cold search through a persisted grocery
list, completed in 0.24s real wall-clock, with build_schedule itself
contributing an unmeasurably small fraction of that.

HONEST QUALITY FINDING FROM REAL DATA, REPORTED RATHER THAN HIDDEN PER
THE TASK'S OWN "IF GREEDY PRODUCES OBVIOUSLY POOR PLANS, SAY SO"
INSTRUCTION: the real five-day run's own day 5 (Kumpir, match_score
0.33, can_cook=false, four missing ingredients) is a materially weaker
pick than days 1-4. This is a genuine, expected greedy characteristic —
locally-optimal early choices consume the strongest candidates and the
best-fitting proteins/cuisines first, leaving a thinner, weaker field
for whichever day comes last — not a bug in this run's own logic.
Recorded here as a real, known limitation of the chosen algorithm
class, exactly as the task asked for, rather than smoothed over in the
final report.


3. CUISINE: A SCORING SIGNAL, DELIBERATELY NEVER A HARD FILTER, FOR A
   REASON SPECIFIC TO THIS FEATURE
=============================================================
search_recipes' own cuisine parameter is a hard, exact-match filter
(confirmed by reading its docstring directly) — every other caller in
this codebase that wants "recipes of cuisine X" uses it that way. This
orchestrator deliberately never does: hard-filtering the candidate pool
to one cuisine would make "avoid the same cuisine on consecutive days"
structurally impossible to satisfy at all, since there would be nothing
else to alternate with. cuisine is passed as None to search_recipes'
own hard filter and instead shapes scoring only, via the same learned-
preference lookup (get_user_profile's own cuisine_preferences, looked
up exactly the way agent/nodes/match_rank.py already does) — confirmed
directly in a real orchestration test
(test_cuisine_is_never_passed_as_a_hard_filter_to_search_recipes).


4. avoid_ingredients: A REAL HARD FILTER THIS FEATURE HAD TO BUILD
   ITSELF, SINCE search_recipes DOESN'T OFFER ONE
=============================================================
Checked directly: search_recipes has no avoid_ingredients parameter at
all — only dietary_filters, max_cook_time, cuisine, meal_type,
max_results, pantry_ingredients. Since multi-day planning is fully
deterministic (no LLM judgment step to hand a soft "avoid this if you
can" instruction to, unlike a single recommendation's own reason node),
avoid_ingredients had to become a real, code-enforced hard filter in
the orchestrator itself: every candidate's full ingredient set (matched
+ missing + partial — the union match_ingredients' own three lists
already represent, extracted here rather than requiring a second
get_recipe call per candidate) is checked via the same
normalize_ingredient pipeline every other ingredient comparison in
this project already uses, and any candidate touching an avoided
ingredient is excluded outright before ever reaching the scheduler.


5. protein_type: DERIVED, NOT STORED — AND WHY THE PRIVATE WHOLE-WORD
   MATCHER WASN'T IMPORTED TO GET IT
=============================================================
No recipe in this corpus carries a stored "protein" field. protein_type
is derived per candidate the same way seed.recipe_parsing.
assign_importances derives a recipe's own CRITICAL ingredient: the
first ingredient (in match_ingredients' own returned order) whose
normalized name is a whole-word match against PROTEIN_TERMS (a public
constant, reused directly — no term list duplicated). The whole-word
check itself is reimplemented as three inline lines rather than
importing seed.recipe_parsing's own private _matches_any_term_whole_
word: that function is private to a module meant for one-time seeding
scripts, and three lines against an already-public constant wasn't
worth crossing that module's own privacy boundary for. This is the
same "chicken thighs" and "chicken breast" both count as "chicken"
principle the protein-variety CAP depends on to mean anything at all —
matching by the TERM, not the ingredient's own full name.


6. OUTPUT: create_grocery_list REUSED, NOT REIMPLEMENTED, PLUS A REAL
   SERVINGS-SCALING DECISION
=============================================================
Every assigned day's own missing ingredients (cross-referenced against
a real get_recipe call for that day's own base quantity/unit/
importance — one call per DAY, not per candidate, since only the
scheduler's own final picks need this level of detail) feed one single
create_grocery_list call across the whole week, exactly reusing the
existing deduplication/section-grouping/is_staple logic rather than a
second aggregator — the task's own explicit instruction, followed
literally. Quantities are scaled from each recipe's own real
servings_base to the plan's target servings via a plain float multiply
(quantity * (servings / servings_base)) — deliberately NOT round-
tripped through scale_recipe's own human-formatted quantity_display
strings ("1 1/2"), which exist for a person to read, not for a numeric
field create_grocery_list expects to bind directly.

total_distinct_ingredients counts EVENTS' worth of distinct missing-
ingredient NAMES across the whole plan, not a quantity sum — the same
"count occurrences, never sum incompatible units" principle phase 9.4's
own waste-stats total_items_wasted already established for an
analogous reason.


7. TESTS: THE PURE SCHEDULER FIRST, THEN A REAL PROBLEM FOUND WHILE
   PROVING THE OVERLAP CLAIM WITH NUMBERS
=============================================================
tests/test_planning/test_scheduler.py exercises every one of the
task's own six named test requirements directly against build_schedule
— no database, no MCP server, no mock needed anywhere in that file,
which is exactly what mealsight.planning's own I/O-free design was
built to allow. Two of those tests failed on the FIRST run, for real,
instructive reasons rather than typos:

    test_protein_variety_respects_the_configured_maximum originally
    gave 5 "chicken" candidates and 5 "tofu" candidates against a cap
    of 2 — but ALL TEN were capped at 2 each (10 candidates, cap=2
    applies per protein_type independently, chicken and tofu are two
    DIFFERENT types) which sounds like it should allow 4 total... the
    actual bug was giving every "other" candidate the SAME single
    protein_type ("tofu"), capping them against EACH OTHER too — fixed
    by giving each of the five non-chicken candidates its own distinct
    protein_type, so 5 days is genuinely fillable (up to 2 chicken +
    5 singly-capped others).

    test_overlap_optimization_uses_fewer_distinct_ingredients_than_
    disabled's first draft picked ingredient sets that happened to
    still need exactly one NEW distinct ingredient in both the
    overlap-on and overlap-off outcomes (a shared item saved on one
    side was exactly offset by a different new item the "winning"
    recipe still needed on that same side) — the two modes produced
    identical distinct-ingredient counts (3 == 3) even though the
    scheduler was behaving correctly the whole time. Rebuilt with a
    hand-computed scenario (documented inline, score arithmetic shown
    in the test's own comments) where the overlap-preferred candidate
    needs ONLY the already-committed ingredient and nothing else new —
    the only shape that can actually demonstrate a real reduction, not
    just a different-but-equally-sized shopping list.

tests/test_agent/test_meal_planner.py needed a more flexible fake than
test_nodes.py's own FakeMCP (which returns one fixed response per
(server, tool) pair) — this orchestrator calls match_ingredients/get_
recipe/calculate_nutrition/check_repetition once PER recipe_id, not
once per tool name, so its own FakeManager accepts either a fixed
ToolCallResult or a per-call callable keyed by the same (server, tool)
pair, letting a test vary its response by whichever recipe_id actually
got called.

9. DECISIONS AND ALTERNATIVES REJECTED
=============================================================
Building a new meal-planning MCP tool (on any of the three servers)
versus zero new tools plus an agent-layer orchestrator
    Rejected a new tool: every piece of data the feature needs already
    existed behind an existing tool, confirmed by reading all 24 first
    — inventing a new tool anyway would have meant either duplicating
    logic that already lives elsewhere, or building the exact cross-
    database shortcut this whole phase was explicitly told not to
    replicate, just moved to a different server.

Wiring meal planning into the existing eleven-node LangGraph pipeline
versus a standalone orchestrator function
    Rejected the graph route: the eleven nodes are shaped around one
    specific flow (perceive -> merge -> match -> reason -> present) that
    multi-day planning doesn't follow at all — no perception step, no
    single LLM-judged choice. Forcing it into that shape would have
    meant either skipping most of the graph's own nodes conditionally
    (fragile, unclear) or accepting steps that don't apply. A second,
    parallel entry point mirroring run_recommendation's own proven
    shape was the more honest fit.

A hard cuisine filter on search_recipes versus a soft cuisine-
preference scoring signal
    Rejected the hard filter: it would have made the plan's own
    cuisine-variety requirement structurally unsatisfiable, since a
    single-cuisine candidate pool has nothing to alternate with.

Treating the protein-variety cap as a scoring penalty (like match_
rank.py's own softer signals) versus a genuine hard filter
    Rejected the soft penalty: only a hard filter can GUARANTEE the
    cap is respected, which is what the task's own test requirement
    ("protein variety respects the configured maximum") actually
    demands — a penalty, however large, can still occasionally lose to
    a strong enough match_score under adversarial data.

Importing seed.recipe_parsing's own private whole-word matcher versus
reimplementing three lines against the public PROTEIN_TERMS constant
    Rejected the cross-module private import: the function is private
    specifically to a module meant for one-time seeding scripts, and
    three lines against an already-exported constant wasn't worth
    crossing that boundary for.

Scaling grocery quantities via scale_recipe's own human-formatted
quantity_display strings versus a plain float multiply against
get_recipe's raw quantities
    Rejected the string route: quantity_display exists to be read by a
    person ("1 1/2"), not parsed back into a float for create_grocery_
    list's own numeric field — a plain scale against the recipe's own
    real base quantity is both simpler and avoids a fraction-string
    round-trip that was never meant to happen in that direction.


10. GLOSSARY
=============================================================
mealsight.planning
    The pure, I/O-free package: PlanCandidate/DayAssignment/
    ScheduleResult/PlanConstraintsUnsatisfiable (models.py) and
    build_schedule (scheduler.py) — never imports mealsight.db,
    mealsight.agent, or any MCP module, enforced by its own __init__.py
    docstring.

mealsight.agent.meal_planner.generate_meal_plan
    The one orchestration entry point, mirroring run_recommendation's
    own manager-reuse contract exactly. Gathers pantry/expiring/
    profile context, builds up to MAX_PLANNING_CANDIDATES=40 enriched
    PlanCandidates via match_ingredients (+ check_repetition for a
    bounded top tier), calls build_schedule, then enriches each
    assigned day (get_recipe, calculate_nutrition) and calls
    create_grocery_list once for the whole week.

use_overlap_optimization / enable_overlap_bonus
    A diagnostic-only toggle threaded from generate_meal_plan through
    build_schedule, existing purely to MEASURE the overlap term's real
    effect (section 8) — always True in real usage; the REST endpoint
    itself never exposes it.

cuisine_repeat_forced (DayAssignment)
    True only on the rare day where excluding the previous day's
    cuisine would have left zero eligible candidates — the one, single
    relaxation build_schedule allows itself before raising
    PlanConstraintsUnsatisfiable outright.

shared_missing_ingredient_names (DayAssignment / MealPlanDay)
    A day's own to-be-bought ingredients that at least one EARLIER day
    in the same plan also needs — the direct, independently-computed
    proof the cross-day overlap optimization did something real,
    rendered on the frontend as the "↺" marker.


11. INTERVIEW TALKING POINTS
=============================================================
Q: You said zero new MCP tools were needed. How confident are you that
isn't just a convenient story — did you actually check, or assume it?

    Checked directly, before writing any planning code at all: read
    every one of the 24 existing tools' own docstrings across all
    three servers first, specifically looking for a genuine gap. There
    wasn't one — search_recipes, match_ingredients, get_recipe, scale_
    recipe, and calculate_nutrition together cover everything the
    scheduler needs to know about a candidate; get_pantry, flag_
    expiring, and create_grocery_list cover the pantry side; check_
    repetition and get_user_profile cover the user-intelligence side.
    If a real gap had turned up — say, no way to learn a recipe's own
    protein without a second full get_recipe call per candidate — that
    would have been a legitimate reason to add one. None did, so I
    didn't add one for its own sake.

Q: Your own report admits day 5 of the real plan was noticeably weaker
than the other four days. Why ship an algorithm with that known flaw
instead of fixing it?

    Because that flaw is an intrinsic, well-understood property of the
    algorithm CLASS the task itself asked for — a greedy, day-by-day
    pass, explicitly instead of an exhaustive search. Any greedy
    scheduler that commits early will sometimes leave a thinner field
    for whichever choice comes last; that's not a bug in this specific
    run, it's what "greedy" means. The honest move, and the one the
    task explicitly asked for ("if greedy produces obviously poor
    plans... say so rather than shipping it silently"), was to run it
    against real data, actually look at what came out, and report the
    real result — including the part that isn't flattering — rather
    than cherry-picking a cleaner-looking example or quietly patching
    the report to omit it.

Q: How do you know the overlap bonus is actually doing something,
rather than just being a formula that looks reasonable on paper?

    Because I measured it against real data instead of trusting the
    formula. The same real candidate pool from the actual live corpus
    was scheduled twice — once with the overlap term active, once with
    it disabled — and the two runs produced genuinely different plans
    (day 4 changed from Peanut Butter Cookies to Pancakes) with a real,
    countable difference in distinct ingredients: 7 versus 9. That's a
    measured ~22% reduction from one real toggle, not an assumption
    that the math must be working because it compiled.
